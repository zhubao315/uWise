# 架构即决策

## 📌 核心定义

> **一句话**：架构的最终产出不是图纸，而是一系列经过审慎权衡的关键决策。

## 🎯 关键要点

- 结构决策：系统如何分解为模块、服务和组件
- 技术决策：选择什么语言、框架、数据库、中间件
- 流程决策：团队如何协作、交付、部署
- 标准决策：编码规范、API 设计准则、数据格式
- 架构漂移：没有明确决策记录，系统在无数次微小变更中逐渐偏离初始设计意图

## 📖 详细说明

### 概念解释
**一句话**：架构的最终产出不是图纸，而是一系列经过审慎权衡的关键决策。
在软件架构领域，许多人将"架构"等同于系统拓扑图、组件图或技术选型文档。但《架构师启示录》深刻揭示了一个被长期忽视的真相：架构的本质是决策。

每一个架构决策都是一次权衡——在多个合理方案之间做出选择，并承担选择带来的后果。架构师的核心职责不是画出漂亮的架构图，而是做出正确的、可追溯的、可演进的决策。这些决策包括但不限于：

- **结构决策**：系统如何分解为模块、服务和组件
- **技术决策**：选择什么语言、框架、数据库、中间件
- **流程决策**：团队如何协作、交付、部署
- **标准决策**：编码规范、API 设计准则、数据格式

架构决策具有几个关键特征：

1. **高影响性**：架构决策一旦做出，变更成本极高，影响面极广
2. **不可逆性**：许多架构决策具有"单向门"性质，难以回头
3. **权衡性**：没有完美方案，每个决策都是利弊权衡的结果
4. **上下文依赖性**：最优决策高度依赖于具体的业务场景、团队能力和组织约束

真正的架构师会将决策过程文档化（如架构决策记录 ADR），使决策的背景、选项和理由可追溯，让后来者理解"为什么"而不仅仅是"是什么"。
