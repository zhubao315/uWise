# 可验证工作流吞吐量

> 人月不再是软件工程的主要度量单位。新的单位是：可验证工作流的吞吐量。

## 📌 核心洞察

《人月神话》揭示了软件不是线性劳动力问题。Bun 的案例揭示了智能体也不是线性数量问题。

真正重要的不是有多少工程师，也不是开多少个 agent，而是组织能否建设这种能力：

1. **需求→规格** — 把模糊意图转化为精确规格
2. **规格→任务** — 把规格分解为原子任务
3. **任务→可并行工作流** — 把任务编排为可并行执行的工作流
4. **工作流→编译器/测试/评审/反馈** — 接入完整的验证管道
5. **失败→流程回流** — 把失败信号反馈回流程本身

## 🎯 关键要点

- **人月是19世纪的度量**，对应泰勒制工厂的线性人力叠加
- **Agent 数量是2023年的度量**，对应 LLM 爆发初期的粗暴缩放
- **可验证工作流吞吐量是下一个度量**，对应工程化、系统化的 AI 协作

### 组织能力的五个层级

| 层级 | 能力 | 度量 |
|------|------|------|
| L1 | 单个 agent 独立完成任务 | 任务完成率 |
| L2 | 多个 agent 按固定流程协作 | 流程通过率 |
| L3 | 可验证工作流 + 质量门 | 工作流吞吐量 |
| L4 | 失败自动回流 + Self-Play 进化 | 系统自愈率 |
| L5 | 跨域调度 + 安全爪 + 无人驾驶 | 人工补位率 |

### 可搭建的结构（不依赖模型厂商）

- `PORTING.md` / `LIFETIMES.tsv` — 任务清单与依赖矩阵
- 对抗评审 — 红队思维验证
- 测试闭环 — 自动化质量门（G0/G1/G2）
- CI 闭环 — 持续集成验证
- 失败自动回流 — 失败即反馈
- 人类总控 — Operator 签字兜底
