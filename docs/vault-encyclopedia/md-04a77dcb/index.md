# 火鸡问题

## 📌 核心定义

> 火鸡问题（Turkey Problem）是纳西姆·塔勒布《随机漫步的傻瓜》中的归纳谬误模型：火鸡被喂了 1000 天，每天都能用"确凿的统计证据"归纳出"人类爱我"的结论——直到第 1001 天（感恩节）被宰杀。**过去的成功记录不能证明策略的安全性，可能只是黑天鹅还没来。**

## 🎯 关键要点

- **归纳的陷阱**：P(安全 | 过去 N 天安全) 在肥尾分布下不随 N 线性增长——**黑天鹅到来前，所有证据都指向"安全"**
- **1000 天幻觉**：经验越长，归纳结论越"坚固"，离真相可能越远（火鸡第 999 天比第 1 天更确信"人类爱我"）
- **与均值回归的对偶**：均值回归说"极端表现会回落"（短期规律），火鸡问题说"安全记录不保证安全"（尾部警告）——共同构成对"历史外推"的双重警告
- **火鸡检查**：对"一直安全/一直赚钱"的资产与体系定期拷问——"如果明天发生极端事件，它会怎样？"
- **识别标准**：答案="可能归零/不可恢复" → 你是感恩节前的火鸡 → 增加冗余（备份/分散/现金垫）

## 📖 详细说明

### 概念解释

火鸡问题揭示了"用历史频率估计风险"的结构性缺陷：在正态世界里，1000 天无事故确实大幅降低了事故概率；但在肥尾世界（市场/技术/组织），极端事件的分布没有"历史频率"可言——**它可能从未发生过，但这不代表它不会发生**。

火鸡的悲剧不在于"没观察到危险"（它每天都观察到喂食），而在于**它把"没出事"误读为"不会出事"**。对投资/职业/系统的翻译：把"过去 N 年一直赚钱/一直安全"当作"未来也安全"的证据，就是在重复火鸡的归纳。

### 实际应用

1. **季度火鸡检查**：对每个"一直安全"项标注"极端情景 + 恢复路径"
2. **备份/冗余纪律**：可恢复性（备份/归档/现金垫）就是火鸡的"逃生门"——没有逃生门的"一直安全"都是裸奔
3. **系统迁移**：知识库 8 月爆发月的连续成功 = 火鸡的 1000 天——检查"目录大改/Syncthing 冲突/硬件故障"情景下的可恢复性
4. **组织迁移**：公司"连续 N 年增长"的叙事同样是火鸡归纳——增长环境消失时的预案在哪？

## 💡 个人理解

火鸡问题最锋利的地方：它不是"信息不足"，是**信息充足但解读错误**——火鸡每天拿到的数据都是真的（人类确实每天喂食），错的是从数据到结论的跳跃。我的 8 月爆发月就是这样的 1000 天：每次复盘都"确凿"地证明体系安全，但"目录结构/Syncthing/硬件"三条极端路径从未被压力测试过。
